# План курсової роботи — «Система контролю та опіки тварин»

## 1. Тема та проблема

**Тема:** Вебсайт для реєстру та підтримки бездомних тварин студентського
містечка, який також організовує волонтерську опіку над ними.

**Проблема предметної області:** інформація про те, які тварини живуть на
території кампусу, де саме, у якому вони стані та чи потребують допомоги —
розпорошена між студентськими чатами й переказами з вуст в уста. Через це
складно зрозуміти, кому потрібна допомога просто зараз і хто вже опікується
конкретною твариною.

## 2. Сутності предметної області

| Сутність | Опис |
|---|---|
| Тварина (Animal) | стабільний ідентифікатор, ім'я, вид (кіт/пес), локація на кампусі, статус («потребує допомоги» / «під опікою»), опис |
| Локація (Area) | категорія-прив'язка тварини до місця на кампусі (гуртожиток, корпус, спортивний комплекс тощо) |
| Заявка на догляд (CareRequest) | у майбутньому пов'язуватиме волонтера з конкретною твариною та періодом опіки (буде реалізовано в Л 3.1) |

## 3. Групи користувачів і сценарії

| Група користувачів | Потреба | Основний сценарій |
|---|---|---|
| Небайдужий студент | Дізнатися, які тварини є на кампусі | Переглянути реєстр і статус тварин |
| Волонтер | Взяти тварину під опіку | Обрати тварину та подати заявку на догляд |
| Координатор (студентська рада/куратор) | Організувати системну опіку | Опрацювати заявки волонтерів, оновити статуси |

### Сценарій: перегляд реєстру тварин

- Користувач: небайдужий студент
- Передумова: відкрито застосунок
- Кроки:
  1. Користувач переходить до секції реєстру.
  2. Переглядає ім'я, вид, локацію та статус тварини.
  3. Знаходить тварину, яка потребує допомоги зараз.
- Результат: користувач розуміє, якій тварині і де саме потрібна допомога.
- Альтернатива: реєстр порожній — застосунок пояснює відсутність даних.

## 5. Маршрути застосунку (реалізовано в Л 2.2)

| Адреса | Компонент | Зміст |

| Інші адреси | `NotFoundPage` | Пояснення невідомого маршруту |

## 6. Що реалізовано зараз (Л 1.1)

- Локальні дані про 4 тварини (`src/data/animals.js`).
- Компонент картки тварини (`src/components/AnimalCard.jsx`).
- Початкова сторінка з секціями «Про застосунок» і «Реєстр тварин»
  (`src/pages/HomePage.jsx`).
- Базове оформлення, адаптивна сітка карток.

Маршрутизація, форми, автентифікація та серверна частина — **не
реалізовані навмисно**, це заплановано на наступні лабораторні (Л 2.2, Л 3.1,
Л 3.2 відповідно до таблиці етапів вище).

## 7. Модель заявки та правила (Л 3.1)

Головна редагована сутність — заявка на догляд (`CareRequest`): `id`, `animalId`, `schedule` (10–500 символів), `visitsPerWeek` (ціле 1–7), `needsSupplies` (обов'язково позначена для понад 4 візитів на тиждень). Повна таблиця правил, власники даних і контракти операцій — у `docs/component-architecture.md`, розділ 8.

Дані заявок з Л 3.2 зберігаються асинхронним сервісом (див. розділ 8).

## 8. Доступ до даних (Л 3.2)

| Сценарій | Статус |
|---|---|
| Створення, перегляд, редагування, видалення заявок | Реалізовано асинхронно (mock із `localStorage`) |
| Стани завантаження, помилки й повтор читання | Реалізовано |
| Блокування повторного подання, збереження введення при відмові | Реалізовано |
| Фільтри й сортування у URL | Збережено з Л 3.1 |
| REST адаптер (`fetch`) | Підготовлено за контрактом, фактичне підключення не виконано |
| Довідник тварин | Локальний (`data/animals.js`) |

Модель збереження: основне джерело — mock сервіс із ключем `animal-care.care-requests.v1` у `localStorage` (залежить від origin: схема, хост, порт). Режим перемикається змінною `VITE_DATA_SOURCE` (`mock` | `api`), адреса API — `VITE_API_BASE_URL`. Власний backend не розроблявся.

## 9. Завершення (Л 4.1): головний сценарій, готовність, захист

### Головний наскрізний сценарій

Волонтер вибирає тварину в реєстрі → відкриває форму заявки → подає некоректні
поля, виправляє й зберігає → бачить підтверджені деталі за поверненим `id` →
змінює графік чи кількість візитів → знаходить результат у списку (пошук,
фільтр, сортування, порожній результат) → скасовує, потім підтверджує
видалення перевірочного запису.

| Дія | Контрольна умова | Де перевіряємо |
|---|---|---|
| Вибрати тварину | Правильний `animalId` у формі | Браузерний прохід, тест нової заявки |
| Подати некоректні поля | Помилки біля полів, команди запису немає | Тест логіки, компонента й інтеграції |
| Створити заявку | Перехід за `id`, поверненим сервісом | Інтеграційний тест |
| Змінити заявку | Той самий `id`, нові поля в деталях і в списку | Інтеграційні тести |
| Скасувати видалення | Сервіс не викликано | Інтеграційний тест |
| Підтвердити видалення | Вилучено саме потрібний запис | Інтеграційний тест |
| Відновитися після відмови | Введення (форма) чи запис (видалення) збережено | Компонентний та інтеграційний тест |
| Перезавантажити URL | Коректний маршрут і збереження | Preview, той самий origin |

### Сценарій показу (захист)

1. Пояснити проблему: інформація про тварин кампусу розпорошена, волонтеру важко зрозуміти, кому потрібна допомога.
2. Відкрити реєстр, знайти тварину зі статусом «Потребує допомоги», перейти до заявки.
3. Подати порожню форму (помилки), виправити поля, зберегти.
4. Показати деталі створеної заявки, змінити графік або візити, знайти результат у списку.
5. Показати пошук, фільтр, сортування, порожній результат і «Показати всі заявки».
6. Скасувати видалення, потім підтвердити видалення **власної перевірочної** заявки (не `req-001`/`req-002`).
7. Показати тести (`npm run test:run`) і пояснити межу сервісу: підміняється `careRequestService`, а не компоненти.
8. Показати `npm run build` + `npm run preview`, результат вимірювання продуктивності й обмеження (mock, немає синхронізації між вкладками).

Демонстраційні записи — `req-001`, `req-002` (початковий набір). Відновлення:
`localStorage.removeItem('animal-care.care-requests.v1')` на потрібному origin.

### Межі рішення

Власний backend не розроблявся. Фактична інтеграція з REST API не перевірялась.
Довідник тварин локальний і лише читається. Заявка означає запит на догляд, а
не підтверджену опіку, її збереження не змінює `needsCare` тварини.
