# Компонентна архітектура — «Система контролю та опіки тварин»

## 1. Що змінилося після Л 1.1

| Було в Л 1.1 | Стало в Л 1.2 | Причина |
|---|---|---|
| Заголовок, навігація й footer в `App.jsx` | `AppLayout`, `SiteHeader`, `MainNav` | Спільне компонування окремо від сторінок |
| Перевірка масиву й `map` прямо в `HomePage` | `Section`, `CatalogSummary`, `AnimalList` | Сторінка лише складає готові блоки |
| Статус (`needsCare`) обчислювався всередині картки | `CareStatusBadge` | Одне правило статусу для картки й макета заявки |
| Тільки реєстр тварин | `CareRequestPage` + `CareRequestFormPreview` | Другий сценарій — підготовка заявки на догляд, без збереження даних |
| Плоска папка `components/` | Групи `layout/`, `navigation/`, `animals/`, `requests/`, `ui/` | Зрозуміла відповідальність файлів |

Початковий сценарій Л 1.1 (перегляд реєстру тварин) повністю збережено —
змінилась лише внутрішня організація коду, а не поведінка для користувача.

## 2. Ієрархія компонентів

```
App
  AppLayout
    SiteHeader
      MainNav
    main
      AnimalSelectionProvider (Context API, лише робоча область)
        CatalogContainer → HomePage
          Section (про застосунок)
          Section (реєстр тварин)
            CatalogSummary
            AnimalFilters
            AnimalList
              AnimalCard (для кожного запису, локальний detailsOpen)
                CareStatusBadge
              EmptyState (якщо порожньо або немає збігів)
        CareRequestContainer → CareRequestPage (власник draft, useEffect)
          Section (підготовка заявки)
            CareStatusBadge
            CareRequestForm
              FormField (для кожного поля)
              AppButton (кнопки)
            CareRequestSummary
    footer
```

`HomePage` і `CareRequestPage` передаються в `AppLayout` через `children` —
оболонка не імпортує ці сторінки напряму.

## 3. Контракти ключових компонентів

| Компонент | Вхідні властивості | Домовленість |
|---|---|---|
| `AppLayout` | `title`, `links`, `children` | Створює спільну оболонку з одним `main` |
| `Section` | `id`, `title`, `children` | `id` унікальний у поточному документі |
| `AnimalList` | `items`, `selectedId`, `onSelect`, `emptyTitle` | Не зберігає власної копії вибору |
| `AnimalCard` | `item`, `selected`, `onSelect` | `detailsOpen` — локальний стан, `selected` — ззовні |
| `AnimalFilters` | `query`, `onlyNeedsCare`, `onQueryChange`, `onOnlyNeedsCareChange`, `onReset` | Керовані значення, компонент нічого не зберігає сам |
| `CareStatusBadge` | `needsCare` | Логічне значення, компонент нічого не змінює |
| `CareRequestPage` | `item`, `onClearSelection` | `item` може бути відсутнім (порожній результат) |
| `FormField` | `id`, `label`, `hint`, `children` | Вкладене поле отримує той самий `id` |
| `CareRequestForm` | `idPrefix`, `animalName`, `draft`, `onScheduleChange`, `onNeedsSuppliesChange`, `onReset` | Повністю кероване; не тримає власного стану полів |
| `CareRequestSummary` | `animalName`, `draft` | Лише показує той самий об'єкт `draft` |
| `AppButton` | `children`, `type`, `variant`, `disabled`, `onClick`, aria-* | `variant`: `primary` або `secondary` |
| `AnimalSelectionProvider` | `items`, `children` | Єдиний власник `selectedId` у робочій області |

## 4. Приклади повторного використання

- **`CareStatusBadge`** використовується і в `AnimalCard` (кожна картка реєстру),
  і окремо в `CareRequestPage` над формою заявки — зміна правила підпису
  статусу тепер відбувається в одному місці й одразу видно в обох.
- **`Section`** використано тричі з різним вмістом (опис застосунку, реєстр
  тварин, заявка на догляд) — оболонка секції однакова, вміст різний.
- **`FormField`** застосовано для двох різних полів форми (`input` для назви
  тварини, `textarea` для графіка догляду) без дублювання розмітки підпису
  й підказки.

## 5. Оформлення

Використано власні стилі з Л 1.1, доповнені правилами для навігації,
кнопок і полів форми (`src/index.css`). React Bootstrap не підключався —
власних стилів достатньо для поточного обсягу інтерфейсу.

## 6. Стан і взаємодія (Л 2.1)

### Карта стану

| Значення | Природа | Власник |
|---|---|---|
| `animals` | Початкові предметні дані | Модуль `data/animals.js`, підключений на рівні `App` |
| `detailsOpen` | Локальний стан інтерфейсу | Конкретна `AnimalCard` |
| `query`, `onlyNeedsCare` | Стан інтерфейсу каталогу | `HomePage`, через хук `useAnimalFilters` |
| `selectedId` | Спільний стан вибору | `AnimalSelectionProvider` (Context API) |
| `draft` | Незбережені поля заявки | Поточний екземпляр `CareRequestPage` |
| `visibleItems`, `selectedItem` | Похідні значення | Обчислюються з даних і стану, окремого `useState` немає |

### Область Context API

`AnimalSelectionContext` + `AnimalSelectionProvider` обгортають лише робочу
область (`CatalogContainer` і `CareRequestContainer`) усередині `children`
`AppLayout`. `SiteHeader`, `MainNav` і footer поза цією областю — вибір тварини
їм не потрібен. `useAnimalSelection` кидає помилку, якщо викликаний поза
провайдером — це помилка інтеграції, а не порожній вибір.

### Контракти подій

| Подія | Відправник | Власник | Дія |
|---|---|---|---|
| `onSelect(id)` | `AnimalCard` | `AnimalSelectionProvider` | Встановлює `selectedId`, якщо `id` існує |
| `onQueryChange(text)` | `AnimalFilters` | `useAnimalFilters` (у `HomePage`) | Оновлює текст пошуку |
| `onOnlyNeedsCareChange(flag)` | `AnimalFilters` | `useAnimalFilters` | Оновлює прапорець фільтра |
| `onScheduleChange(text)` | `CareRequestForm` | `CareRequestPage` | Оновлює `draft.schedule` |
| `onNeedsSuppliesChange(flag)` | `CareRequestForm` | `CareRequestPage` | Оновлює `draft.needsSupplies` |
| `onReset()` | `CareRequestForm` | `CareRequestPage` | Повертає `draft` до порожнього об'єкта |
| `onClearSelection()` | `CareRequestPage` | `AnimalSelectionProvider` | Скидає `selectedId` до `null` |

### Обґрунтування вибору засобів керування станом

| Потреба | Засіб | Чому |
|---|---|---|
| Розгортання опису картки | Локальний `useState` | Потрібне лише одному екземпляру `AnimalCard` |
| Пошук і фільтр у каталозі | Стан сторінки через власний хук `useAnimalFilters` | Значення потрібні лише фільтрам і списку одного сценарію |
| Поля й підсумок чернетки | Піднято до `CareRequestPage` | Форма і підсумок — сусідні компоненти, яким потрібен один об'єкт |
| Вибір тварини між каталогом і заявкою | Context API (`AnimalSelectionProvider`) | Дві віддалені гілки робочої області мають бачити один вибір |
| Видимі записи, лічильники | Звичайні обчислення | Похідні значення з поточних даних і фільтрів |
| Заголовок вкладки | `useEffect` | Синхронізація із зовнішньою властивістю браузера (`document.title`) |

Ефект у `CareRequestPage` синхронізує `document.title` з назвою обраної
тварини. Залежність — обчислений рядок `title`; функція очищення повертає
попередній заголовок перед повторною синхронізацією або демонтуванням.
Redux/MobX/Zustand не використовувались — для цього обсягу стану вистачає
`useState`, підняття стану й обмеженого Context API.


## 7. Маршрутизація (Л 2.2)

### Дерево маршрутного вмісту

```
AppLayout (Outlet, AnimalSelectionProvider)
  Головна (/)
  Реєстр тварин (/animals)
  Деталі тварини (/animals/:animalId)
  RequestsLayout (/requests, свій Outlet)
    Список заявок (index)
    Нова заявка (/requests/new)
    Редагування заявки (/requests/:requestId/edit)
  Сторінка 404 (*)
```

`AppLayout` не має власного `path` — він задає лише спільне компонування
(шапку, меню, `AnimalSelectionProvider`) для всіх дочірніх маршрутів через
`Outlet`. `RequestsLayout` додає другий рівень `Outlet` лише там, де потрібне
власне меню розділу (список/нова заявка).

### Де тепер живе стан після Л 2.1

| Значення | Було в Л 2.1 | Стало в Л 2.2 |
|---|---|---|
| Відкрита сторінка | Всі секції змонтовані одночасно | Шлях URL (`Routes`/`Route`) |
| Пошук і фільтр `needsCare` | `useState` у хуку `useAnimalFilters` | Query parameters (`useSearchParams`), той самий контракт хука |
| Тварина для нової заявки | Тільки Context API | `?animalId=` у query — читається напряму, не копіюється в контекст |
| Останній явний вибір (підсвітка картки) | Context API | Залишається Context API (`AnimalSelectionProvider`) |
| Чернетка форми, розгортання опису | Локальний `useState` | Без змін — локальний `useState`, скидається при демонтуванні |
| Заголовок вкладки | `useEffect` у `CareRequestPage` | Перенесено в спільний `PageHeading`, викликається кожною сторінкою |

Пряме відкриття `/animals?q=соня` чи `/requests/req-001/edit` відновлює
потрібний стан з адреси без участі Context API — це навмисно різні механізми:
контекст пам'ятає **останню дію користувача**, URL визначає **поточну
сторінку**.

### Контракти нових компонентів

| Компонент | Вхідні властивості | Домовленість |
|---|---|---|
| `PageHeading` | `title` | Єдиний власник `document.title` для відкритої сторінки |
| `AnimalListPage` | `items`, `selectedId`, `onSelect` | Колишній вміст каталогу з `HomePage`, тепер окрема адреса |
| `AnimalDetailsPage` | `items` | Читає `animalId` через `useParams`, показує `NotFoundPage` за відсутності |
| `RequestsLayout` | — (`Outlet`) | Власне меню розділу заявок, без нового провайдера |
| `CareRequestPage` | `title`, `item`, `initialDraft`, `onCancel`, `cancelLabel` | Спільний редактор; `item` завжди коректний — перевірку виконує маршрутна сторінка |
| `CareRequestCreatePage` | `items` | Читає `animalId` з query; без параметра показує `EmptyState` |
| `CareRequestEditPage` | `requests`, `items` | Читає `requestId` через `useParams`; подвійна перевірка (заявка → тварина) |
| `NotFoundPage` | `title`, `message` (необов'язкові) | Один компонент для невідомого маршруту й відсутнього запису |

`CareRequestContainer` з Л 2.1 видалено — його роль тепер виконують
`CareRequestCreatePage` і `CareRequestEditPage` з явними адресами.

## 8. Форми, валідація й операції з даними (Л 3.1)

### Модель заявки на догляд і правила полів

| Поле | Правило |
|---|---|
| `id` | Стабільний ідентифікатор (`req-<uuid>`), створюється операцією додавання, у формі не редагується |
| `animalId` | Посилання на наявну тварину реєстру |
| `schedule` | Обов'язковий текст; після видалення крайніх пробілів від 10 до 500 символів (`.length`) |
| `visitsPerWeek` | Обов'язкове ціле число від 1 до 7 включно |
| `needsSupplies` | Логічне значення; для понад 4 візитів на тиждень позначка обов'язкова (частий догляд потребує планування корму чи ліків) |

Заявка означає запит на догляд, а не підтверджену опіку. Збереження заявки не змінює `needsCare` тварини. Це правила нашої предметної області, а не загальні вимоги.

### Власники даних

| Дані | Власник | Коли змінюються |
|---|---|---|
| Довідник тварин (`data/animals.js`) | Модуль даних | У Л 3.1 не редагується |
| Колекція заявок | `CareRequestsProvider` | Після успішного створення, оновлення чи видалення |
| Чернетка полів | Поточний `CareRequestPage` | Під час введення й відновлення початкових полів |
| Ознаки `touched`/`attempted`, помилка операції | Поточний `CareRequestPage` | Після взаємодії та спроби збереження |
| Пошук, фільтр, порядок списку | URL (`?q=`, `?supplies=`, `?sort=`) | Після зміни параметрів подання |
| Видимі заявки | Обчислення (`useCareRequestFilters`) | З поточної колекції та параметрів, без окремого стану |

Імпорт `data/careRequests.js` з Л 3.2 використовує лише mock сервіс для початкового наповнення (поки ключ у `localStorage` відсутній). Сторінки читають спільну колекцію через `useCareRequests`.

### Контракти операцій (у Л 3.1 синхронні; з Л 3.2 асинхронні — див. розділ 9)

| Операція | Вхід | Успіх | Відмова |
|---|---|---|---|
| `createRequest` | Поля заявки | `{ ok: true, record }` | `{ ok: false, errors }` (помилки полів) |
| `updateRequest` | Ідентифікатор і поля | `{ ok: true, record }` | Помилки полів або `{ ok: false, message }` (запис відсутній) |
| `deleteRequest` | Ідентифікатор | `{ ok: true }` | `{ ok: false, message }` (запис відсутній) |
| Перегляд | `requestId` з маршруту | Знайдений запис | `NotFoundPage` |

Підтвердження видалення — у `useDeleteCareRequest` (`window.confirm`), операція `deleteRequest` браузерного діалогу не містить, тому в Л 3.2 її можна підключити до асинхронного рівня без змін інтерфейсу. Скасування повертає `{ ok: false, cancelled: true }` і не вважається помилкою.

### Повторне використання форми

Одна пара `CareRequestPage` + `CareRequestForm` обслуговує створення (`/requests/new`) і редагування (`/requests/:requestId/edit`). Відмінності передаються через props: `title`, `initialDraft`, `onSave`, `submitLabel`, `onCancel`. Ключ `key` на маршрутній сторінці прив'язаний до тварини чи запису, тому перехід між записами створює нову чернетку. Правило валідації одне — `validateCareRequest`; його викликають і редактор, і операції колекції.

### Два порожніх випадки списку

- Порожня колекція (`requests.length === 0`): пояснення й перехід до реєстру тварин.
- Порожній результат (записи є, збігів немає): окреме пояснення й кнопка «Показати всі заявки».

### Маршрут деталей заявки

Додано `/requests/:requestId` (`CareRequestDetailsPage`): перегляд запису зі спільної колекції, редагування, видалення. З Л 3.2 адреса збереженої заявки відкривається й після перезавантаження (у тому самому origin), бо дані зберігає mock сервіс.

## 9. Рівень доступу до даних (Л 3.2)

### Схема залежностей

```
Сторінки та форми (CareRequestPage, CareRequestEditPage, RequestsPage, ...)
        ↓
CareRequestsProvider / useCareRequests
        ↓
careRequestService  (єдине місце вибору реалізації)
        ↓
mockCareRequestService  або  apiCareRequestService
        ↓
localStorage браузера  або  зовнішнє REST API
```

### Межі відповідальності

| Частина | Відповідальність | Чого не знає |
|---|---|---|
| `CareRequestForm` | Поля, повідомлення, стан подання (`isSubmitting`) | URL, HTTP, ключ `localStorage` |
| Маршрутні сторінки | Параметри маршруту, сценарій, перехід після підтвердженого успіху | Формат мережевого пакета |
| `CareRequestsProvider` | Знімок колекції, стани читання й запису, повтор, захист застарілих відповідей | Спосіб збереження всередині адаптера |
| `careRequestService` | Вибір реалізації за `VITE_DATA_SOURCE` | JSX, навігація |
| Mock / API адаптер | Читання, запис, перетворення даних, помилки | Стан полів форми |
| `careRequestValidation` | Предметні правила й нормалізація | React, мережа, сховище |

### Джерело, знімок, чернетка

- **Джерело** — `localStorage` (mock) або API; переживає перезавантаження.
- **Знімок** — `requests` у провайдері: підтверджені дані для інтерфейсу. Змінюється лише після успіху сервісу.
- **Чернетка** — поля форми в `CareRequestPage`; не входить до сервісу й не переживає демонтування.

### Контракт сервісу заявок на догляд

Команди запису отримують нормалізовані поля без `id` (`animalId`, `schedule`, `visitsPerWeek`, `needsSupplies`). Усі ідентифікатори — рядки.

| Метод | Успіх | Відмова |
|---|---|---|
| `getAll({ signal })` | Масив заявок, зокрема `[]` | Виняток сервісу або скасування (`AbortError`) |
| `getById(id, { signal })` | Одна заявка | `NOT_FOUND` для відсутнього запису |
| `create(input)` | Повний збережений запис із `id` | `VALIDATION`, запису або з'єднання |
| `update(id, input)` | Повний оновлений запис із тим самим `id` | Зокрема `NOT_FOUND` |
| `delete(id)` | `undefined` після підтвердження | Зокрема `NOT_FOUND` |

Провайдер перетворює відмову запису на `{ ok: false, message, errors, code }`, успіх — на `{ ok: true, record }`. Форма змінила спосіб очікування (`await`), але не модель помилок з Л 3.1.

Коди помилок `ServiceError`: `VALIDATION`, `NOT_FOUND`, `BAD_DATA`, `NETWORK`, `HTTP`, `CONFIG`, `STORAGE_READ`, `STORAGE_WRITE`, `MOCK_FAILURE`.

### Стани інтерфейсу

| Стан | Що показано | Що не стверджується |
|---|---|---|
| `loading` | «Завантаження заявок…» (`CareRequestsGate`) | Що записів немає |
| `success`, непорожній | Дані та дії | Автоматична синхронізація з іншими клієнтами |
| `success`, порожній | Пояснення й перехід до реєстру тварин | Що сталася помилка |
| `error` | Причина й «Спробувати ще раз» | Що джерело повернуло порожній список |
| Триває запис | «Збереження…» / «Опрацювання зміни…», блокування дій | Що зміни підтверджені |
| Відсутність збігів | «За цими умовами нічого не знайдено» (лише після успішного читання) | Що колекція порожня |

### Захист від повторних і застарілих дій

- `mutationLock` (ref) блокує другий запис одразу, до наступного рендеру; `isMutating` лише відображає стан.
- Читання має номер версії та `AbortController`: старіша відповідь не затирає новіший знімок. Початок запису скасовує активне читання.
- Маршрутні сторінки не переходять після закриття (`pageAlive`) і після зміни `requestId` (`activeId`).
- Скасування видалення не викликає сервіс; відмова залишає запис у колекції.

### Вибір способу читання деталей

Основний варіант — спільний знімок провайдера (`useCareRequests`): список, деталі й редактор читають одну колекцію, відсутність запису визначається після завершення читання (`CareRequestsGate`). Хук `useCareRequestRecord` (окреме `getById` із `AbortController`, `ignore` і порівнянням `id`/`attempt`) підготовлено й перевірено на швидкій зміні `requestId`, але у фінальний маршрут не підключено, щоб не мати двох незалежних копій деталей. Підходить, коли список стане частковим (пагінація) або маршрут має читати лише один запис.

### Межі синхронізації

Власний запис одразу оновлює знімок, «Оновити дані» перечитує джерело. Зміни іншої вкладки чи користувача автоматично не надходять. Без версій записів простий `update` застосовує останню прийняту команду і не виявляє всіх конфліктів редагування. Якщо змінена заявка перестала відповідати фільтру, вона зникає з результатів — це не втрата даних.

## 10. Інтеграція, тестування й остаточні рішення (Л 4.1)

### Рівні перевірки

| Рівень | Що підмінено | Що залишено справжнім |
|---|---|---|
| Логіка (`validateCareRequest`, `selectCareRequests`) | Нічого | Чисті функції |
| Компонент (`CareRequestPage`) | Обробник `onSave` | Форма, валідація, стан подання |
| Інтеграція (`App`) | Модуль `careRequestService` (`vi.mock`), `window.confirm` | Маршрути, провайдер, сторінки, форми, фільтри |
| Адаптер (`apiCareRequestService`) | Глобальний `fetch` (`vi.stubGlobal`) | Перетворення запиту/відповіді, помилки |
| Браузерний прохід (preview) | Нічого | Збірка, mock з `localStorage`, перезавантаження адрес |

Підміна сервісу не доводить роботу фактичного API; jsdom не вимірює швидкодію.

### Мутаційна перевірка тестів

Тест, який не падає при дефекті, нічого не доводить, тому код свідомо ламали:

| Внесений дефект | Результат |
|---|---|
| `reload` не очищує повідомлення про успіх | Виявлено (регресійний тест) |
| Межа `> 4` змінена на `>= 4` | Виявлено |
| Перехід після створення за вигаданим `id` | Виявлено |
| `AppButton` не передає `disabled` | Спочатку **не виявлено** (подання захищає `fieldset`, а кнопки видалення — ні); додано тест блокування дій під час видалення |

### Знайдені й виправлені дефекти

- Після невдалого повторного читання над помилкою лишалось старе «Заявку видалено.» — `reload` тепер очищує повідомлення.
- Однакова пара «ref + effect» актуальності сторінки була в п'яти місцях — винесено в `useMountedRef`.
- Правила відбору й сортування вийшли з хука URL у чисту `selectCareRequests`: їх тестують без маршрутизатора.
- Навчальні кнопки відмов (`DevFailureControls`) прибрано з демонстраційного інтерфейсу; відмови тепер відтворюють тести.

### Рішення щодо даних джерела

Адаптер перевіряє **структуру** прочитаних записів (типи, унікальні `id`), а не предметні межі (діапазон візитів, довжина графіка). Історичний запис із порушенням меж відображається, але не можна зберегти його редагування, не виправивши поля. Це свідома межа, а не гарантія коректності джерела.

### Продуктивність: вимірювання й рішення

Гіпотеза: після дії, що змінює лише допоміжний стан (закриття повідомлення), усі рядки таблиці заявок перемальовуються без потреби.

| Умова | Значення |
|---|---|
| Набір даних | Реальний — 2; стрес-набір — 500 заявок у `localStorage` |
| Режим | Розробка (`npm run dev`), `Profiler` навколо `CareRequestTable` (тимчасово); у dev-режимі діє `StrictMode` |
| Дія | Закриття повідомлення про видалення; ввід тексту в пошук |
| Метрика | Сума `actualDuration` оновлень таблиці, медіана 6 повторів |

| Набір | Без `memo` | З `memo` + `useCallback` |
|---|---|---|
| Реальний | 5.1 | 6.0 мс |
| 500 заявок | 270.9 мс | 289.4 мс |

Рішення: На реальному обсязі різниці немає, тому мемоізацію в основний код не додано; варіант із CareRequestRow у memo і стабільними обробниками збережено окремим патчем docs/memoization-experiment.patch і пройшов усі тести. 

Варіант з мемоізацією (`CareRequestRow` у `memo`, стабільні `handleDelete`, `deleteWithConfirmation`, `deleteRequest`, `mutate`) пройшов усі тести, зокрема перевірку, що після редагування список показує нові поля, а не застарілий рядок. Застосування патча: `git apply --ignore-whitespace docs/memoization-experiment.patch` (на Windows з CRLF — з прапорцем); скасування: `git checkout -- src` до коміту. `useMemo` для відбору й сортування не додавався: вимірювання не показало, що саме обчислення є вузьким місцем.

### Підсумок меж

Mock сервіс у `localStorage`; немає синхронізації вкладок і виявлення конфліктів; REST адаптер лише за контрактом; повний аудит доступності не виконувався; Docker для тестів у цьому етапі не запускався.
